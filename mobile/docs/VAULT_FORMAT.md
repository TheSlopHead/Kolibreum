# Мобильный формат архива v2

`vault.json.version = 2` выбирает криптографический режим. JSON-схема каталога и `manifest.json` backup имеют собственный `version = 1`; они не выбирают режим шифрования. Неизвестные версии отклоняются.

| Параметр | Мобильный v1, чтение для миграции | Мобильный v2 |
| --- | --- | --- |
| KDF сущности | HKDF-SHA256, info=`mut:object<uuid>` | HKDF-SHA256, info=`mut:<kind>:<uuid>` |
| HKDF salt | UTF-8 vault UUID | UTF-8 vault UUID |
| AEAD AAD | UTF-8 UUID сущности | UTF-8 `<kind>:<uuid>` |
| kind | Криптографически отсутствует | `object` или `snapshot` |
| Envelope | nonce 24 байта + ciphertext + Poly1305 tag 16 байт | То же представление |

Папки `objects/xx/<uuid>` и `snapshots/<uuid>` отображаются на домены `object` и `snapshot`. Оригиналы и миниатюры обложек — объекты. Одинаковый UUID у сущностей разных типов даёт разные ключи; проверяется и правильный ключ с неправильным AAD. Ключи берутся из случайного 32-байтового master через HKDF-SHA256. Password wrapping остаётся Argon2id + XChaCha20-Poly1305 с AAD vault UUID; recovery wrapping — случайный 32-байтовый секрет и AAD `vaultUUID:recovery`.

В v2 ошибки AEAD не запускают повторное открытие с v1 KDF/AAD. Замена только version в header на 1 приводит к отказу аутентификации v2 snapshot. Подстановка ciphertext импортированного JSON-файла вместо snapshot не проходит AEAD.

## Миграция мобильного v1

После проверки пароля/recovery и каталога проверяются все достижимые оригиналы (AEAD, размер и SHA-256, если записан) и обложки (AEAD, лимит). Каждая сущность перешифровывается в `.migrate-<uuid>` с прежним UUID и новым KDF/AAD. Заголовок переключается на 2 только в staging. Staging повторно открывается и проверяется до переноса.

Источник целиком остаётся в `vault.v1`, включая исторические snapshots/недостижимые объекты. Активный v2 содержит текущий каталог и его достижимые объекты. Пароль/recovery envelopes, vault UUID, оригинальные байты, метаданные, полки, настройки, прогресс и закладки сохраняются. Plaintext не пишется на диск. Маркер `vault.migration` позволяет вернуть v1 после прерывания между двумя directory renames; незавершённый staging не принимается за рабочий архив. Существующая `vault.v1` не перезаписывается.

V1 backup сначала проверяется в исходном виде: paths, manifest, точный граф и AEAD/размер/hash. Затем он мигрирует в staging и только после повторной проверки заменяет рабочую библиотеку. Предыдущая рабочая библиотека сохраняется в `vault.previous` по прежним правилам restore.

V1 не может подтвердить тип сущности криптографически. Миграция не определяет, был ли каталог подменён до открытия, и не делает исторические v1-копии защищёнными по v2. Возврат к согласованным старым header/HEAD/ciphertext с прежней версией/паролем требует отдельной модели rollback protection; он не предотвращается этим изменением.

## Независимые Go-векторы

`tool/go_vectors.go` — проверочный скрипт внутри `mobile/`; Go-ядро `internal/vault/` не изменяется. Он генерирует `test/fixtures/go-vault-v2.json` с одинаковым UUID для object/snapshot, разными ключами, AAD и ciphertext. `-version=1` воспроизводит прежний вектор без изменения его байтов. Обычные Flutter-тесты не требуют Go; они читают готовые JSON-векторы.

`flutter test --no-pub tool/verify_go_v2.dart` дополнительно передаёт созданный Dart-кодеком ciphertext скрипту Go для проверки AEAD и исходных байтов. Для этой отдельной команды нужен Go и зависимости модуля.

В Go-коммите `c3ba874` HKDF уже использует `mut:<kind>:<id>`, однако snapshot AAD — только UUID и header ещё 1. Поэтому эти проверки устанавливают совместимость криптографических примитивов с мобильным контрактом, а не совместимость полного архива с текущим Go-приложением.
