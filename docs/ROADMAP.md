# Roadmap реализации

Порядок важнее дат. Оценка для одного разработчика с кодовыми агентами: первый демонстрационный прототип — 4–8 недель, закрытая beta — ещё 8–16 недель **при условии** регулярной работы; криптографический аудит, упаковка и реальные книги могут сдвинуть сроки. Нельзя пропускать проверку восстановления ради внешнего вида.

## Фаза 0 — критерии и визуальная система (1–2 недели)

- 3–5 разговоров с друзьями, которые реально поставят приложение: размер и форматы их коллекции (включая форматы без встроенного чтения), текущая программа, опыт потери файлов, отношение к резервным копиям. Без вопросов о готовности платить — монетизация не в фокусе v1.
- Прототип экранов: пустая библиотека, полка с 300 книгами, PDF/EPUB/FB2, карточка «нет встроенного чтения», блокировка, копия, восстановление. Дизайн-токены: цвет, шрифты, радиусы, интервалы, состояния фокуса, иконки; светлая и тёмная тема.
- Замер целевой среды: Ubuntu LTS, Fedora, Debian; версия WebKitGTK и сборка Wails v2. Выбрать минимально поддерживаемые версии в ADR.
- Выход: все опрошенные друзья понимают, где открыть книгу и создать копию без подсказок; короткое README/демо-видео сценария для GitHub вместо посадочной страницы — это портфолио-артефакт, а не маркетинговый материал.

## Фаза 1 — технический вертикальный срез (2–4 недели)

- Go core без UI: создать сейф, импортировать 1 EPUB + 1 PDF + 1 FB2, закрыть, открыть, экспортировать, сделать и восстановить копию на чистом каталоге.
- Версия формата, тестовые векторы, `vaultctl verify/restore`, crash test замены snapshot. Проверка пароля и recovery key.
- Окно Wails: список книг, открыть одну книгу каждого формата, навигация и возврат; оценка потребления памяти PDF.js / epub.js / WebKitGTK.
- Выход: после восстановления байты трёх файлов совпадают с исходными; зашифрованная папка не содержит названий и открытых обложек; приложение работает без сети.

## Фаза 2 — пригодная личная библиотека (4–8 недель)

- Массовый импорт, ошибки и дубликаты, обложки, полки, позиции чтения, закладки, поиск по названию/автору, виртуализация списка, клавиатура и HiDPI.
- Потоковая обработка крупных файлов, отмена импорта, лимиты парсеров, блокировка по таймеру, проверка копии и отчёт.
- Реальные тестовые наборы: обычные, битые, многоязычные файлы; 1/100/1000/10 000 книг; слабый ноутбук. Корректность важнее заранее придуманного benchmark.
- Выход: 8 из 10 участников самостоятельно импортируют набор и восстанавливают его на другом ПК; UI не зависает на большой книге; серьёзные ошибки потери данных отсутствуют.

## Фаза 3 — закрытая beta и доверие (4–8 недель)

- .deb и второй формат упаковки после smoke test; CI для целевых дистрибутивов; проверка сигнатур и зависимостей, доступный репорт ошибок без содержания книг.
- Security review формата и обработки EPUB/PDF/FB2, fuzzing, исправление находок. Документация по восстановлению, спецификация формата и CLI; тест миграции v1 → будущая версия.
- Сайт: видео сценария «импорт → чтение → копия → восстановление», реальные скриншоты, модель угроз, честная политика данных, FAQ о пароле и DRM. Публичная beta только после успешной проверки копий.
- Выход: ни один известный критический дефект сохранности/утечки не открыт, восстановление проверено вне машины разработчика, обратная связь beta сгруппирована по повторяемым проблемам.

## Фаза 4 — после подтверждения спроса

- «Полка без файлов» и импорт/экспорт собственных заметок.
- Капсула для выборочной передачи файлов после правовой оценки, проверки ключа получателя и тестов совместимости формата.
- Локальный AI: сначала вопрос по одной книге с цитатой, затем по библиотеке; только opt-in, полностью офлайн тест.
- Платная инфраструктура: сначала удалённые зашифрованные копии с проверкой восстановления; затем синхронизация/доставка. До разработки — оценка стоимости хранения, поддержки и платежей, отдельная модель угроз сервера.

## Бэклог, который нельзя протащить в v1 незаметно

OCR, сканирование бумажных книг, обход DRM конкретных магазинов, совместное редактирование, публичные профили, рекомендации, внутренняя лента, маркетплейс, мобильное приложение, облачный AI, полноценная система заметок, межкнижный семантический поиск, Windows/macOS. Для каждой новой функции требуется один пользовательский сценарий, стоимость поддержки и изменение модели угроз.

Новые адаптеры чтения (MOBI/AZW3 без DRM, CBZ/CBR, DjVu, TXT/Markdown, DOCX — список и обоснование в ARCHITECTURE.md) добавляются по одному за спринт, каждый со своим тестовым корпусом и лимитами импорта; хранение файла в сейфе от наличия адаптера не зависит и доступно для любого формата уже в v1.

## Как работать с кодовыми агентами

Репозиторий начинается с `README.md`, этих четырёх документов, `spec/format.md` (после исследования) и ADR. Каждое нетривиальное решение (выбор примитива шифрования, отказ от адаптера, граница капсулы и т.д.) фиксируется коротким ADR с причиной и альтернативами — это не бюрократия, а тот самый материал, который потом хорошо читается в портфолио и на собеседовании. Задачи небольшие и имеют входные/выходные критерии. Один агент разрабатывает изолированный пакет, другой может делать ревью/тестирование, но криптографическую схему не принимать по одному ответу агента. Не складывать в промпты реальные книги, секреты или пользовательские ключи.

Рекомендуемая последовательность задач:

1. Каркас Wails v2/Go/Svelte, линтеры, сборка Ubuntu и Fedora, фиксированные версии зависимостей.
2. Чистые Go-интерфейсы сейфа и тест восстановления с фиктивными текстами.
3. Тестовый набор форматов с лицензированными/собственными образцами и опасными входами.
4. Три адаптера чтения, каждый за одним интерфейсом и с отдельными лимитами.
5. Дизайн-система и экраны по утверждённым состояниям, визуальные снимки в CI.
6. Подключение Go к UI узкими методами; проверка блокировки и отсутствия исходящего трафика.
7. Нагрузочные тесты, упаковка, независимое security review, beta.

### Definition of Done для каждого изменения

Код форматирован, статические проверки проходят, есть необходимые тесты поведения/восстановления, ошибки понятны пользователю, интерфейс проверен с клавиатурой и в двух темах, диагностические логи не раскрывают содержимое, миграция/обратная совместимость рассмотрена. Для криптографии и сохранности нужны воспроизводимые тестовые векторы и ревью другим человеком.

## Решения на контрольных точках

- После фазы 0: не «стоит ли продолжать» (проект не зависит от размера рынка), а понятны ли друзьям-тестерам основные сценарии без подсказок; если нет — правится дизайн, а не позиционирование.
- После фазы 1: можно ли обеспечить безопасный рендеринг EPUB и переносимое восстановление в выбранном стеке; при неудаче меняем адаптер/стек до расширения функционала.
- После beta: если когда-либо возникнет интерес к платной удалённой синхронизации — оценивать отдельно и не раньше; до этого момента вопрос сервера и тарифов не рассматривается.
